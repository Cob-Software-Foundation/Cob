# Cob Language v0.0.5

## Added

### SQLite3 / Tcl / Tk bindings — six new keywords in cob_interp

The vendored `vendor/SQLite`, `vendor/TCL`, and `vendor/TK` trees have
been sitting in the repo since v0.0.4, buildable but not reachable from
Cob source at all (no keywords, nothing in the grammar). This release
wires all three into the language:

```
sql_open(<path>)          -> handle (int, 0 on failure)
sql_exec(<handle>, <sql>) -> rc (int, 0 on success)
sql_query(<handle>, <sql>)-> string (first column of first row, "" if none)
sql_close(<handle>)       -> 0

tcl_eval(<script>)        -> string (Tcl's string result)
tk_eval(<script>)         -> string (same interpreter as tcl_eval, plus Tk)
```

All six are call-style builtins parsed the same way `harvest(<bytes>)`
already was: a bare keyword directly followed by `(`. `sql_exec` and
`sql_query` are the only two-argument builtins Cob has ever had; the
parser change that makes that possible is generic (comma-separated
arg list) but only wired up for these two keywords for now.

Example:

```
set h = sql_open("scores.db")
set rc = sql_exec(h, "CREATE TABLE IF NOT EXISTS t (name TEXT)")
set rc = sql_exec(h, "INSERT INTO t VALUES ('cob')")
set name = sql_query(h, "SELECT name FROM t LIMIT 1")
pop("got: " + name)
sql_close(h)

pop("6*7 = " + tcl_eval("expr {6*7}"))
```

**Opt-in by design, not bundled into the default binary.** Plain
`make cob_interp` still builds with zero extra dependencies, exactly
like every prior release — calling any of the six keywords there
prints a one-line warning (`sql_open() is a stub in this build...`)
and evaluates to a harmless `0`/`""` instead of failing to compile or
crashing. The real implementation only compiles in via a new target:

```
make sqlite tcl tk       # build the vendored libraries first
make cob_interp_db       # cob_interp.c + -DCOB_WITH_SQLITE -DCOB_WITH_TCL -DCOB_WITH_TK
```

`tcl_eval()`/`tk_eval()` share one lazily-created, process-wide Tcl
interpreter, so state built up across several calls (variables,
widgets) persists for the life of the program. `tk_eval()` needs a
real X11 `$DISPLAY` at runtime for actual widget commands; without one
it fails the same way `wish` would headless (a normal Tcl error
string returned to the caller), it does not crash the interpreter —
verified both ways, see below.

`.strawberry` cache format bumped `COBSTRW3` -> `COBSTRW4` to add the
six new expression kinds. A cache written by an older cob_interp is
just treated as a miss and silently regenerated, same handling as any
other magic mismatch.

### Makefile fix: vendor directory casing

`make sqlite`, `make tcl`, and `make tk` referenced `vendor/sqlite`,
`vendor/tcl`, `vendor/tk` (lowercase), but the actual checked-in
directories are `vendor/SQLite`, `vendor/TCL`, `vendor/TK`. On a
case-sensitive filesystem (any Linux/macOS box) all three vendor build
targets failed outright with "No such file or directory" before ever
reaching a compiler. Found while building the libraries to verify the
new keywords above; all three Makefile targets now point at the real
paths and were confirmed to build clean end-to-end (see below).

### Makefile fix: `cob_interp_db` didn't actually support Windows

The first pass at `cob_interp_db` only worked on Linux/macOS — it
unconditionally used `vendor/TCL/unix` and `vendor/TK/unix`, linked
`-lX11`, and assumed Unix-style library names (`libtcl9.0.a`,
`libtcl9tk9.0.a`). On Windows (MSYS2/MinGW) that fails immediately:
Tk's Windows build doesn't use X11 at all, there is no `X11/Xlib.h` to
find, and the whole `unix/` build tree is the wrong one to use.

Tcl and Tk both ship a **separate** `win/` build tree for MSYS2/MinGW
(`vendor/TCL/win`, `vendor/TK/win`), distinct from `unix/`. Confirmed
by actually cross-building the entire chain with a Linux-hosted
`x86_64-w64-mingw32` toolchain (`gcc-mingw-w64-x86-64`) — this is real
cross-compilation, not guesswork about how the Windows build should
look:

* The Windows static libs are named differently than Unix's:
  `libtcl90.a` / `libtcl9tk90.a` (no dot before "90"), vs.
  `libtcl9.0.a` / `libtcl9tk9.0.a` on Unix.
* Tk's Windows build resolves its internal `#include <X11/Xlib.h>`
  through its own `vendor/TK/xlib/` shim header (found via include
  search path, not a macro) rather than a real Xlib — no X11 dev
  headers/libs needed or wanted on Windows.
* Compiling against the static libs needs `-DSTATIC_BUILD=1` (Tcl/Tk's
  Windows headers otherwise mark every function `dllimport`, which
  fails to link against a static `.a`). Even with that defined, Tk
  still resolves through Tcl's stub mechanism internally, so both the
  real library *and* its matching `*stub.a` have to be linked for Tcl
  and for Tk (`libtcl90.a` + `libtclstub.a`, `libtcl9tk90.a` +
  `libtkstub.a`) — omitting the stub libs fails to link even though
  the real symbols are present in the other archive.
* Windows needs a different system library set entirely: `-lnetapi32
  -lkernel32 -luser32 -ladvapi32 -luserenv -lws2_32 -lgdi32
  -lcomdlg32 -limm32 -lcomctl32 -lshell32 -luuid -lole32 -loleaut32
  -lwinspool` — no `-lX11 -ldl -lpthread -lz` (Windows Tcl bundles its
  own zlib).

The Makefile now branches on `$(OS)` the same way it already did for
`EXE_SUF`: `tcl`, `tk`, and `cob_interp_db` all pick the right build
tree, include paths, defines, and link flags per platform, so
`make sqlite tcl tk && make cob_interp_db` produces a correct build
whether run under a Linux/macOS shell or an MSYS2/MinGW shell on
Windows — same commands either way, no platform-specific instructions
needed at the command line.

### Makefile fix: `configure` couldn't find a C compiler on w64devkit

A real-world Windows build hit `configure: error: no acceptable C
compiler found in $PATH` running `make tcl`, even though the exact
same `cc` worked fine for every other target in this Makefile.
Reproduced the root cause directly (not guessed): installed BusyBox
and fed its `ash` a real Windows-style `PATH`
(`C:\...;C:\...;C:\...`) — every `which`/PATH-based lookup fails,
because BusyBox's shell splits `$PATH` on `:`, and a Windows `PATH`
has neither `:`-separated entries nor unambiguous drive letters (`C:`
itself contains a `:`). w64devkit's bundled `sh` (BusyBox ash) hits
exactly this when `configure`'s own compiler-detection loop
(`checking for gcc... / checking for cc... / ...`) tries to locate a
compiler via the shell's normal command lookup — even though the
*outer* `make` invocation, running as a native Windows program, sees
`PATH` correctly.

Fixed by passing `CC="$(CC)"` directly into the `configure`
invocation for both Tcl and Tk, on both platforms: autoconf's
`AC_PROG_CC` skips its entire detection loop when `$CC` is already
set in the environment, sidestepping the broken lookup instead of
trying to fix BusyBox's PATH parsing itself.

### Makefile improvement: `make cob_interp_db` now builds its own dependencies

`sqlite`, `tcl`, and `tk` were `.PHONY` targets that always re-ran in
full, and `cob_interp_db` didn't depend on any of them — building it
meant remembering to type `make sqlite tcl tk` first, every time, in
the right order. They're now real file targets keyed on the actual
library each one produces (`vendor/SQLite/libsqlite3.a`, `$(TCL_LIB)`,
`$(TK_LIB)`), and `cob_interp_db` lists them as prerequisites. One
command, `make cob_interp_db`, now builds everything it needs the
first time and skips anything already built on later runs. `make
sqlite`/`make tcl`/`make tk` still exist as convenience aliases for
the same underlying file targets, for anyone who wants to build one
piece at a time.

### Added: `_cobwindow` — a second, dependency-free GUI option

```
window_open(<title>)            -> handle (int, 0 on failure)
window_label(<handle>, <text>)  -> 0 (sets/replaces the in-window text)
window_wait(<handle>, <seconds>)-> 0 (keeps the window responsive for ~<seconds>)
window_close(<handle>)          -> 0
```

```
shuck cobwindow
set h = window_open("Cob Window Demo")
set rc = window_label(h, "Hello from Cob!")
set rc = window_wait(h, 5)
set rc = window_close(h)
```

Added as a lighter-weight alternative to `tk_eval()` for the common
case of "just show a window with some text" — no vendored source
tree, no `configure`/`make`, no autoconf, no busybox-ash PATH
gotchas. It links directly against the OS's own windowing API:
`user32`/`gdi32` on Windows (part of every Windows install, nothing
to build), Xlib on Linux/macOS-with-X11 (needs the same X11 dev
headers `tk` already documents, but no build step of its own).
Built via a new target, `make cob_interp_window` — no prerequisites
needed first, unlike `cob_interp_db`.

`shuck cobwindow` is a deliberate no-op: there's no real
`cobwindow.cob` file to read, but writing `shuck cobwindow` at the top
of a script that uses these four keywords reads naturally, so
`cob_load_library()` special-cases the name and just acknowledges it
(printing a warning if the binary wasn't built with
`COB_WITH_COBWINDOW`, so the gap is visible at parse time rather than
only when a keyword silently no-ops later). Same opt-in-by-default
philosophy as the SQLite/Tcl/Tk bindings: a plain `cob_interp` prints
a one-line warning and returns a harmless default for each of the
four keywords rather than failing to build or crashing.

The window's close button ([X]) is intentionally swallowed on both
platforms — Cob has no callback mechanism to notify a running script
that the user clicked it, so the window just keeps running until
`window_wait()`'s timer runs out or `window_close()` is called
explicitly, the same "explicit close only" model `harvest()`/`trash()`
already use for memory.

`.strawberry` cache format bumped again, `COBSTRW4` -> `COBSTRW5`, to
add the four new expression kinds.

### CI: new `test_extensions` / `test_extensions_windows` jobs

`.github/workflows/build.yml` had no coverage at all for
`cob_interp_db`/`cob_interp_window` — every bug fixed in this release
(the `vendor/sqlite` casing mismatch, the `unix/`-vs-`win/` vendor
tree mismatch, the busybox PATH issue) would have shipped silently
without a human happening to try building them. Two new jobs:

* `test_extensions` (Linux, real build): installs `libx11-dev` and
  `xvfb`, builds `cob_interp` (plain) / `cob_interp_db` /
  `cob_interp_window`, and smoke-tests all three: the plain binary's
  stub-and-warn fallback, `cob_interp_db` against real SQLite +
  real Tcl, and `cob_interp_window` actually opening a real (headless,
  via Xvfb) X11 window and reading back its handle.
* `test_extensions_windows` (Linux runner, mingw-w64 cross-compile):
  builds both the `win/`-tree `cob_interp_db` and the dependency-free
  `cob_interp_window` for Windows and asserts the output is a valid
  PE32+ binary. Can't execute the result (no Windows runner, no
  display) — this catches build regressions, not runtime ones.

## Fixed

### `popcorn_comp`: Windows `system()` quoting bug in bundled-Zig auto-resolve

Repro:

```powershell
./popcorn_comp.exe smoke_test.strawberry -o temp.exe --no-gc
```

with a `zig\` folder present next to `popcorn_comp.exe` (auto-resolve
path, no `--cc` given) failed with:

```
'C:\...\zig\zig.exe" cc -std=c99 ... ' is not recognized as an internal or external command
```

**Root cause:** `find_bundled_zig_cc()` (`src/popcorn_comp.c`) returns
a pre-quoted compiler string (`"path" cc`). `cob_spawn_compile()` then
appends further quoted arguments (`-o "out" "in"`), producing a
command line with multiple separate quoted tokens that starts with a
quote. `system()` on Windows hands this to `cmd.exe /c <string>`,
which strips only the first and last `"` of a command line that
starts with a quote — not matching pairs — corrupting the line. The
explicit `--cc "zig\zig.exe cc"` path was never affected, since a
user-supplied `--cc`/`$CobCC` string isn't pre-quoted and doesn't
start with `"`.

**Fix:** in `cob_spawn_compile()`, on Windows, if the assembled
command starts with `"`, wrap the whole command in one more pair of
quotes before calling `system()` — the standard workaround for this
`cmd.exe` behavior. `--cc`/`$CobCC` invocations are untouched (they
don't hit the new branch). Only `src/popcorn_comp.c` changed for this
fix; `cob_interp` and `farmer` are unaffected by it.
