About

A language built for the last mile of a small program.

Cob exists for the programs that don't need a framework — a script you want to run fast today and hand someone a real binary for tomorrow.

Why Cob

Most small utility scripts end up stuck between two bad choices: an interpreted language that's fast to write but needs a runtime installed everywhere it runs, or a systems language that's fast to run but slow to write. Cob is built to close that gap for genuinely small programs — Python-style indentation for the part you write quickly, and a real path to a standalone native binary for the part you ship.

That's why the toolchain is split into three single-purpose tools instead of one do-everything binary. cob_interp runs a program directly while you're writing it, with a bytecode cache so re-runs boot fast. popcorn_comp takes that same bytecode and produces a real, standalone executable when you're done — no bundled runtime, no "install Cob to run this file." farmer fetches libraries other people have written, so you're not starting from nothing.

Why its compiler is a real compiler

Earlier versions of popcorn_comp statically linked TCC's compiler source directly into the binary. That worked, but it meant Cob was carrying its own C compiler internals — a maintenance burden with no upside once a better option existed. As of v0.0.3, popcorn_comp transpiles to plain C and spawns Zig's zig cc as a subprocess instead. Zig bundles libc and CRT files for essentially every target in one install, which is what turns cross-compiling into a single -target flag rather than a separately installed toolchain per platform. Every release bundles Zig next to popcorn_comp, so a downloaded Cob compiles with nothing else installed; building from source, put Zig on your PATH or point --cc at any C compiler you already have.

The corn theme, briefly

The naming isn't just decoration — it's meant to make the mental model legible. shuck pulls in a library the way you'd shuck an ear of corn to get at what's inside. harvest and trash are manual memory allocation and freeing, gated behind --no-gc because they're a deliberate, opt-in escape hatch, not the default. The .strawberry cache and farmer harvest <package> keep the same vocabulary consistent through the whole toolchain instead of switching metaphors halfway through.

What it can do today

Cob is still small on purpose, but it is past the toy stage. Variables hold numbers or strings. while loops and if / elif / else blocks share one set of conditions, and pop prints any expression. As of 0.0.9 it has functions (recipe and serve) and an interactive REPL. Past that core, everything is a corn-themed standard library of real shared libraries you bring in with shuck: porch for console input, kernels for text, cornmath, almanac for time, granary for files, pantry for SQLite, barn for native windows with real buttons, sliders, and text boxes, and tassel for Tcl/Tk. They are ordinary extern libraries, so you can write your own the same way. You can try the core language right now in the browser playground, which runs the interpreter as WebAssembly with nothing to install.

Where it's headed

The honest gaps are mostly about the compiler and the safety net around it. popcorn_comp compiles the whole language, recipes and the standard library included, but a program that uses library modules must be linked dynamically, and cross-compiling one needs those modules built for the target. Only some targets get an executed test in CI, and the regression suite is not wired into CI yet. The cards below say where each of those stands.

Where things stand

Stated plainly, the way the project's own release notes do.

Shipped

Real compiler backend

popcorn_comp spawns Zig (or any --cc override) instead of embedding TCC, and every release bundles Zig so it works with nothing else installed. It compiles the same core language the interpreter runs.

Shipped

In-process package extraction

farmer unzips via a statically linked miniz, with zip-slip protection tested against a real malicious archive.

Shipped

A corn-themed standard library

SQLite, native windows, widgets, Tcl/Tk, console input, text, numbers, time and files, as shared libraries loaded with shuck: porch, cornmath, kernels, almanac, granary, pantry, barn, tassel. Began as built-in keywords in 0.0.5; became the standard library in 0.0.9.

Shipped

Functions and a REPL

recipe and serve define and return from functions, with recursion and call checking before a program runs; cob_interp with no file starts an interactive session. Shipped in 0.0.9.

Shipped

C API and an in-browser playground

extern binds a Cob name to an exported C function, and the pure-language core compiles to WebAssembly for the playground. Shipped in 0.0.6; the playground gained console input in 0.0.8.

In progress

Cross-platform CI verification

The 9-target build matrix runs, and the Linux amd64 package is installed and smoke-tested in CI (interpreter and a native compile through the bundled Zig). The other targets are built but not yet executed there.

In progress

Automated test suite

make test runs 17 checks: every program test runs through both the interpreter and the compiler against the same expected output, plus the REPL, every error message, the cache, and the standard library. A stress suite runs nightly in CI. The tests are not wired into CI yet.

Shipped

Compiling SQLite and window programs

Because the standard library is ordinary shared-library calls, popcorn_comp links pantry and barn like any other library. Shipped in 0.0.9; the barn window module has not yet been run against a display in testing.

Planned

Windows ARM32

Cut from the current release: the target Cob's maintainers were least confident Zig fully supports.
